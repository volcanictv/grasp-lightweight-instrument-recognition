Surgical Instrument Classification on GraSP

Status and plan — 2026-09-02

Problem

Classify surgical instruments in GraSP video frames into 7 classes (Bipolar Forceps, Prograsp Forceps, Large Needle Driver, Monopolar Curved Scissors, Suction Instrument, Clip Applier, Laparoscopic Grasper). Localization (finding where an instrument is) is an upstream input this work depends on but doesn't own — the classifier is scoped to: given a frame, or given a detected/segmented instance, say what it is.

Approach

Started with a lightweight baseline (MobileNetV3-Small) doing whole-frame multi-label classification. Two things became clear early: the dataset is severely imbalanced (the rarest class has ~25x fewer examples than the most common), and most frames contain 2-3 instruments at once, which makes "what's in this frame" a much harder, more ambiguous signal for the model to learn from than "what is this specific instrument," given a bounding box. Reframing as per-instance classification (crop-and-classify, given a box) turned out to fix most of the rare-class problem on its own — the same lightweight model went from struggling on the two hardest classes to being competitive on them, just by changing what the model is asked to do with the same input information.

From there, instead of guessing at further improvements, the actual misclassified examples were inspected directly — root cause first, not more architecture. That surfaced two concrete, fixable problems: a handful of instrument pairs that look genuinely similar (confirmed by checking that two independently-trained models make the exact same mistakes on the exact same pairs), and a crop-preprocessing issue where an elongated instrument's most distinctive part gets visually compressed by a fixed-size resize. Each fix was tested as a single, isolated change against a fixed baseline, and reported honestly including when it didn't work.

A number this report briefly reported and then walked back, on purpose — the process is the point. A follow-up weighting scheme (favoring the strongest single model, resnet50_320, at 0.40 instead of a flat 0.25 each) looked like a further improvement on the official test set (macro-F1 0.9031, a broad-looking sweep optimum). Before trusting it, all four models were retrained from scratch on a genuinely separate data split (fold1) and the same weight sweep was repeated on that held-out fold. It did not replicate — the held-out fold actually favored flat weighting slightly over 0.40. That specific weight value had been tuned to the official test set's particular composition, not a real generalizing improvement, so it was reverted. The underlying architecture choices (ResNet-50, the resolution increase, the letterbox crop) were checked the same way and did generalize — every individual model's held-out result lands within about a point of its official-test number. 0.893/0.927 (flat weighting) is the number that survived that check, and is reported here for that reason, not because it was the highest number seen this round.

GPU cost of the current best (4 models combined): ~17ms per instance, negligible. CPU cost is a real, honest trade-off — ResNet-50 is substantially slower than MobileNetV3-Small on CPU specifically (MobileNetV3's whole design point is CPU efficiency; ResNet-50 doesn't have that advantage), on the order of 10-20x based on a clean, uncontended benchmark (an earlier reading of up to 49x turned out to be measurement contention from other jobs running on the same machine at the time, not a real hardware difference). Still far from prohibitive for an offline pipeline, but not the free upgrade the GPU number alone suggests.

What was tried and failed on these two classes specifically

  • Sharper class-reweighting (stronger inverse-frequency loss weight) — recall went up, precision collapsed, net F1 worse.
  • A crop zoomed to just the instrument tip — discarded shaft/context detail these two classes apparently needed; worst result recorded for Laparoscopic Grasper all project.
  • Restricting the letterbox fix to only very elongated crops, combined with sharper weighting — both classes got worse, not recovered.
  • Per-class decision threshold, tuned on all 7 classes at once — the two rarest classes' thresholds were overfit to a handful of training examples and made things worse; net negative.
  • A heavier single backbone (ResNet-50, same preprocessing otherwise) — every class improved, these two most of all. This is the one change that worked, and it's a capacity fix, not a data-imbalance or crop-engineering fix.
  • Averaging the ResNet-50 model with an existing MobileNetV3 checkpoint — free further improvement on top, no new training.

What's actually causing the remaining errors

Checked directly against real misclassified examples, not inferred from aggregate metrics:

  • A handful of visually similar instrument pairs (Bipolar Forceps / Prograsp Forceps; Large Needle Driver / Monopolar Curved Scissors) account for most of the remaining confusion. This shows up identically in two separately-trained models, which is why it reads as a real property of the data rather than one model's quirk.
  • Elongated crops lose their most informative region under a fixed-size resize. Preserving the crop's true proportions instead of stretching it fixed several of the confused pairs directly and measurably.
  • The two rarest classes are fragile in a specific way: they get worse whenever a fix reallocates decision weight toward other classes, and better only when the model gets more capacity to work with. Six different reallocation-style fixes (reweighting, tighter crops, restricted crops, thresholds, and a fine-tuned ensemble weight — see the overfitting check below) all made them worse or didn't hold up — a heavier backbone is what actually helped, and it helped every class, not just these two.
  • The one substantial confusion left (Laparoscopic Grasper / Suction Instrument) has a specific, confirmed physical cause, not vague similarity. Checked real misclassified crops directly: when this instrument's jaws are closed, it's a smooth featureless shaft indistinguishable from a suction tube — there's no visual information left to tell them apart. Correctly-classified examples clearly show an open jaw. Tested whether looking at nearby video frames finds a moment the jaws open (even a wide, ~13-second search) — it doesn't, for the specific cases checked; this isn't fixable by looking harder at the same kind of information.

An overfitting check that caught something real

This round tried ~15-20 configurations, all selected by scoring against the same official test set repeatedly. Rather than trust that, the full winning recipe was retrained from scratch on a separate data split (fold1) and re-evaluated on that split's own held-out cases. The architecture choices — ResNet-50, the resolution increase, the letterbox crop — all generalized cleanly, landing within about a point of their official-test numbers. But a follow-up fine-tuned ensemble weight, which had looked like a further real improvement on official test, did not replicate on the held-out split — it was reverted, and the flat-averaged ensemble (0.893/0.927) is what's reported above as a result. This is the process working as intended: a specific, over-fit number was caught and corrected before being reported as real, rather than after.

Plan forward

  1. Treat upstream localization (detection/segmentation) as a given input, not something to redesign — keep the existing code there working, but it isn't the focus.
  2. Laparoscopic Grasper vs. Suction Instrument's closed-jaw ambiguity is a genuine ceiling for single-frame, single-video-window classification given what's been tried — the next real lever is more training examples of this specific confusion, not another technique applied to the same information.
  3. Get a properly held-out calibration set before trusting per-class decision thresholds beyond the one already validated.
  4. A once-open item, now closed: the CPU-latency discrepancy (two runs of the same architecture had disagreed by 6-49x) turned out to be ordinary system load on a shared 4-core machine, not a benchmarking bug — confirmed with a clean, idle re-measurement.
